# DropMate 내비 기능 지원표 · 서버 알고리즘 비교 (2026-11-12)

검증 수준 표기: **실기기** 실제 차/폰 · **에뮬** Pleos 에뮬레이터에서 화면·동작 확인 · **합성** 합성 테스트만 · **미검증** 코드만 있음 · **없음** 미구현

## 1. 두 프로젝트 비교

| 항목 | 현재 앱 (Downloads\…\DropMate) | 바탕화면 car_app\…\DropMate-home\project |
|---|---|---|
| 구조 | Android 앱 안의 Kotlin 엔진(`engine/`)이 TMAP을 직접 호출. 서버 없음 | Python 서버(`server/`, 296개 파일) + Android 앱. 앱은 `http://127.0.0.1:8765` 등 로컬 서버를 호출 |
| 차에서 단독 실행 | 가능(에뮬에서 확인) | 서버가 같은 기기에 떠 있어야 함. 실제 차·폰에서는 서버 배포가 필요(미준비) |
| A단계(하차점 순위) | 동승자 도착 분 반올림 → 운전자 도착 → 보행 → ID (`DropComparison.kt`) | 도착시각 → 운전자 도착 → 보행 → ID, 비교 기준(comparisonBasis)별로 따로 순위 (`build_selection`) |
| B단계(같은 하차점 경로) | 최소시간·최소환승·최소도보 + 같은 경로 배지 병합 (`RouteOptions.kt`) | 같은 구조(`select_onward`), 빠른 도착 대비 지연(`delayFromFastestSeconds`)도 계산 |
| 운전자 우회 한도 | 900초 고정 | `min(900초, 0.30 × 직행시간)`, 80% 근접 경고, 900초 기준 결과도 함께 기록 |
| 환승 상한 | 없음(2026-11-12 사용자 결정: 빠른 경로 탈락 금지) | 3회 초과는 정책 제외 |
| 선택 유지 | 결과 하나를 그대로 사용, 안내 중 재탐색 시 하차점 경유 유지 | 사용자가 고른 하차점 고정, 실시간 재순위 없음(`KEEP_SELECTED_DROPOFF…`) |
| 최적성 표기 | "전역 최적 아님" 문구 | `globalOptimality='NOT_PROVEN'` |
| 시간 근거 | TMAP 응답(실시간 대기 미반영) | 시간표·실시간·RAPTOR 모듈 별도 존재(이번에 실행 안 함) |
| 테스트 | 엔진 합성 59개 통과(오늘) | `test_phase4_two_stage_policy.py` 13개 오프라인 실행 통과(오늘, 합성) |

**판단**: B단계·선택 유지 규칙은 이미 같은 설계라 서버 코드를 앱에 다시 옮길 필요는 없음. 실제로 다른 것은 **운전자 한도 정책(900 고정 vs 30%)**과 **환승 3회 상한**뿐이며, 둘 다 사용자 결정 사항.

## 3. 흐름 원칙(지시서 반영 예정)
- 홈: 지도 + 운전자 목적지 검색. "동승자 목적지 추가"는 선택이며, 없으면 일반 내비로 동작.
- 작은 도착시간 변화로 하차점을 자동 교체하지 않음(사용자가 고른 하차점 고정).
- 재탐색해도 처음 정한 운전자 우회 한도를 새로 주지 않음.
- Pleos 내장 내비로 안내 중이면 DropMate 음성은 끔(겹침 방지).
