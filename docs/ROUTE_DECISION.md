# 최적 하차 경로 선정 근거

## 실제 요청별 판단 기록 위치
이 문서는 공통 설계 기준이다. 실제 계산 결과의 구체적인 판단 근거는 계산 완료마다 기기의 `Android/data/com.jiye.dropmate/files/outputs/phase4/live/<요청ID>/decision_log.md`에 자동 저장한다. 앱 오른쪽 안내의 ‘판단 기록 저장’에 해당 파일 경로가 표시된다.
기록에는 후보별 출발부터 최종 도착까지의 시간, 하차 완료시각, 접근 도보시간, 운전자 추가시간, 제외·보류 사유, 선택 후보와 다른 후보의 도착 차이, 동률 결정 이유, 미조회 범위와 실시간 정보 미검증 상태가 포함된다. 실제 요청을 실행하지 않은 상태에서 특정 경로를 선택한 이유를 만들어 기록하지 않는다.

## 경로 안내 디자인
결과가 나오면 입력을 접고 넓은 지도와 오른쪽 A~D 비교 카드를 표시한다. A는 동승자 단독 이동, B는 선택된 동승 경로, C는 운전자 직행, D는 선택 경로 이용 시 운전자 도착이다. 노선색은 TMAP routeColor를 우선하고 누락 시 호선 이름 색상을 사용한다. 도보는 노란 점선, 버스는 버스 노선 표식, 지하철은 호선 표식으로 구분한다. 지도 표식과 안내 카드 색상을 일치시킨다. 이 UI 변경은 휠·드래그 입력 코드를 변경하지 않는다.

## 목표
2026-11-05 사용자 확정: 출발지부터 동승자 최종 목적지까지의 총 도착시간을 우선한다. 운전자 직행 대비 추가시간은 min(900초, 직행 × 30%) 이내(2026-11-12 사용자 결정), 하차점부터 첫 탑승 역·정류장까지 실제 접근 보행은 600초 이내다. 연속 도보 구간을 합산하며 소요시간 누락은 미확인으로 제외한다. 종전의 600m 보행 판정을 시간 판정으로 변경했다. 후보 생성의 600m 반경은 호출 절약용 탐색 범위일 뿐 10분 보행 한도가 아니다.
경로 중간 하차(최대 6곳)·운전자 목적지 하차·동승자 목적지(입구) 앞 경유를 요청당 최대 8개 비교한다(2026-11-12 정확도 개선). 직접 데려다주는 경로는 기본 정답이 아니며 제한을 충족하고 비교 후보 중 빨라야 선택된다. 반올림 분 순위 정책은 기존 합의를 유지한다.
운전자 목적지까지의 우회를 제한하면서 동승자의 최종 목적지 도착시각을 최소화한다. 가까운 역이나 짧은 대기시간 자체가 목표가 아니다. 차량 교통상황, 하차, 접근 보행, 승강장 이동, 탑승 가능한 실제 운행편, 환승, 마지막 보행을 모두 고려해야 한다.

## 현재 구현과 한계
- TMAP 차량 경로의 소요시간을 사용한다. 중간 하차 차량시간은 직행 경로의 누적 구간시간이다.
- GTFS 2025는 후보 연결 확인과 조회 우선순위용이며 최종 시간에 더하지 않는다.
- 요청당 최대 8개 후보를 평가하고 기본 14회 호출 상한을 적용한다(목적지 입구를 비교할 때만 그만큼 올림). 따라서 전체 지역의 전역 최적이 아니라 조회·평가된 후보 중 선택이다.
- 평가 가능 후보의 동승자 도착시각을 분 단위 반올림하여 비교한다. 동률이면 운전자 도착시각, 총 보행시간, 후보 ID 순서다.
- 실제 실시간 버스·지하철 운행편은 아직 연결하지 않았다. TMAP 여정의 대기 포함 여부도 미확인이므로 실시간 환승까지 검증한 최적경로라고 해석하면 안 된다.
- 도보 직행은 한도 없이 동승자 도착 시간으로 비교한다(2026-11-12 사용자 결정). 미확정 탑승 여유·역 내부 이동시간은 0으로 대체하지 않는다.
- 목적지 입구: 역은 입구를 쓰지 않는다. 입구 찾는 순서는 주소기반 내비게이션용DB(자료 수령 전) → 카카오 장소 검색 → TMAP 장소 검색 → 입구 파일. 하차점은 입구 그 자리, 내비 목적지는 엔진이 고른 운전자 입구. 자세한 경위는 ENTRANCE_CHANGELOG.md.
- 모든 시간은 조회 시점 실시간 TMAP 기준이며 실제 주행으로 검증하지 않았다.

## 실시간 통합 시 계산
탑승 준비 시각 = 출발시각 + 차량 이동 + 하차 + 정류장/역 접근 보행 + 역 내부 이동 + 탑승 여유.
운행 방향과 노선, 정류장/역 ID가 일치하고 탑승 준비 시각 이후 출발하는 운행편을 선택한다. 첫 차가 이미 지나가면 다음 편을 검토한다. 대기시간은 그 편의 출발시각에서 준비 시각을 뺀 값이다. 최종 도착은 그 편의 이동, 이후 환승과 마지막 보행을 합산해 비교한다.
예를 들어 차량 2분과 접근 보행 3분 뒤, 현재부터 7분 후 출발하는 편이라면 내부 이동·탑승 여유를 제외한 대기는 2분이다. 이 미확정 시간이 있으면 탑승 가능을 확정하지 않는다. 다른 역의 대기가 짧아도 최종 도착이 늦으면 선택하지 않는다.
TMAP totalTime에 실시간 대기를 무조건 더하면 이미 포함된 대기를 이중 계산할 수 있다. 운행편별 분해와 시간 기준을 검증한 뒤 대체해야 한다. 실시간 값 누락·노후화·방향 불일치는 미확인으로 표시한다.

## 호출 절약
이미 조회한 차량·대중교통 선형을 재사용한다. 시각화를 위해 TMAP을 재호출하지 않는다. 실시간 API는 선택 후보와 해당 노선·방향에 한정하고 관측시각과 유효기간으로 캐시한다. 후보는 GTFS로 우선순위를 정하되 GTFS 시간으로 실시간 값을 대체하지 않는다.

## 시각화
파란 실선은 함께 타는 차량 구간, 회색 점선은 하차 후 운전자 구간, 금색 별표는 선택 하차점이다. 동승자 도보는 노란 점선, 대중교통은 노선별 색상과 순서 번호를 사용한다. 상세 안내에는 출발·도착 정류장과 노선을 표시한다. API 선형이 없으면 임의 직선을 실제 경로처럼 표시하지 않는다. 선택 후보가 없으면 기준 경로만 표시하고 별을 만들지 않는다.

## 요청별 기록
앱 외부 파일 디렉터리의 outputs/phase4/live/<요청ID>/decision_log.md에 후보별 상태, 제외 이유, 도착시각, 단독 이동 비교, 선정 범위와 호출 수를 기록한다. API 키와 응답 원문은 기록하지 않는다.

## PC 휠
삭제 대상을 휠로 잘못 해석했던 변경을 되돌렸다. 휠은 커서 기준 최대 ±1단계 확대·축소, 좌클릭 드래그는 지도 이동으로 유지한다. PLEOS는 tools/start-pleos-mouse.cmd의 VirtioTablet,-VirtioMouse 설정으로 실행한다. 사용자가 확대·축소 변경을 명시하기 전까지 코드와 입력 설정을 변경하지 않는다.

2026-11-12 사용자 확정(순위): 동승자 도착(분) → 운전자 우회(분) → 환승 수 → 함께 탄 시간이 긴 하차점 → 총 보행 → ID. 운전자 우회·동승자 이득이 같으면 더 멀리 함께 가는 하차점을 추천한다.
